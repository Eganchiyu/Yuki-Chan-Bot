# YukiV6 桌宠化技术规划文档

> 状态：方案评估与技术规划  
> 目标位置：`future addons` 未来扩展方向  
> 参考原型：`future addons/webpage_agent/yuki_brain.py`、`future addons/webpage_agent/yuki_eye.user.js`

---

## 1. 背景与目标

YukiV6 当前是一个基于 QQ 消息流、长期记忆、精力系统、Function Call 工具链和小女仆子代理的个人智能助手。项目已经具备较强的人格连续性、主动破冰能力、视觉模型调用能力和本地任务执行雏形，因此具备扩展为桌面宠物的基础。

本规划的目标是评估并设计一个未来的桌宠化运行时，使 Yuki 从“聊天机器人”逐步扩展为“住在电脑里的陪伴型 AI 桌宠”。桌宠化后的 Yuki 应具备以下方向能力：

- 常驻桌面，以可视化角色、气泡、动画等形式陪伴主人。
- 感知主人是否在电脑前、是否忙碌、是否长时间未交互。
- 在合适时机主动找主人聊天，而不是只被动回复。
- 主人不在时睡觉、发呆、整理记忆或做低风险的自我活动。
- 在主人授权下进行屏幕截图分析，理解当前屏幕内容并作出回复。
- 在严格权限控制下进行网页读取、网页辅助操作和简单电脑操控。
- 保持所有高风险现实侵入能力可见、可控、可暂停、可审计。

本文件仅为技术文档规划，不进行实际实现。

## 2. 当前项目基础评估

### 2.1 已具备的核心能力

#### 2.1.1 人格与对话中枢

当前项目中的 `core/engine.py` 已承担 LLM 回复生成、工具链调用、表情包搜索、上下文合并等核心职责。未来桌宠不应另起一套人格系统，而应复用现有的 YukiEngine 作为主要对话中枢。

可复用内容：

- LLM 对话接口。
- 工具链多轮调用机制。
- 记忆检索上下文构建。
- 回复清洗与最终输出。
- 表情包/视觉内容理解链路。

#### 2.1.2 精力值、生物钟与主动破冰

`core/brain.py` 中已有精力值、活跃度、回复欲望、生物钟时间权重等机制。这些机制天然适合桌宠化：

- 精力值可以决定 Yuki 是否愿意聊天、是否疲惫、是否睡觉。
- 时间权重可以模拟早晨醒来、午后活跃、深夜睡眠。
- 群聊活跃度可以扩展为“主人活跃度”或“桌面活跃度”。
- 主动破冰机制可以扩展为桌宠主动搭话机制。

未来桌宠状态可以在现有 YukiState 基础上新增：

- 当前桌宠状态。
- 主人是否在。
- 最近一次主人交互时间。
- 最近一次主动搭话时间。
- 主动搭话失败次数。
- 当前屏幕摘要。
- 当前窗口上下文。

#### 2.1.3 视觉模型调用能力

`modules/vision/processor.py` 已有图像压缩、base64 编码、视觉模型调用和缓存逻辑。虽然当前主要用于 QQ 表情包/图片理解，但可以扩展为屏幕截图分析。

需要注意的是，屏幕截图与表情包理解存在本质差异：

- 屏幕截图可能包含大量隐私信息。
- 屏幕截图内容复杂，token 与视觉模型成本更高。
- 屏幕截图需要先做隐私过滤和区域裁剪。
- 桌面场景需要更强的上下文结构化输出，而不是简单情绪描述。

#### 2.1.4 小女仆子代理与本地执行能力

`core/maid.py` 中的小女仆系统已经具备任务分解、编写临时代码、执行脚本、固化技能等能力。这说明项目已经具备“本地环境操作”的基础。

但桌宠化后不应直接把电脑操控接入小女仆自由执行链。原因：

- 小女仆偏向自主编程与任务执行，权限边界较粗。
- 桌面操控涉及真实电脑环境，风险比普通脚本更高。
- 鼠标、键盘、网页提交、文件操作都可能造成不可逆影响。

因此建议新增独立的桌面动作安全层，不让 LLM 或小女仆直接操作电脑。

#### 2.1.5 网页代理原型

`future addons/webpage_agent/yuki_brain.py` 与 `yuki_eye.user.js` 是非常有价值的原型。

当前原型能力：

- 本地 HTTP 服务接收网页快照。
- 浏览器脚本扫描页面交互元素。
- 元素包含 id、tag、type、text、placeholder、href、selector、rect、state、context。
- 后端通过队列下发指令。
- 浏览器脚本轮询 `/poll` 获取动作。
- 支持 click、type、clear、select、scroll、hover、focus、navigate、wait 等动作。

该模式适合升级为正式的 BrowserBridge：

- 浏览器负责 DOM 感知与动作执行。
- Yuki 后端负责决策、权限审查和动作队列。
- 动作执行结果回传后端。
- 后端把结果写入 Yuki 的上下文和记忆。

## 3. 总体可行性结论

桌宠化总体可行性较高，且项目基础明显优于从零开始。

| 能力 | 可行性 | 当前基础 | 主要风险 |
|---|---:|---|---|
| 桌面常驻角色 UI | 高 | Python 项目可接 PySide6 / Qt / Tk / WebView | UI 工程量 |
| 主动找主人聊天 | 高 | 已有主动破冰与精力系统 | 打扰感、时机判断 |
| 睡觉/发呆/自我活动 | 高 | 已有生物钟和日记系统 | 行为设计 |
| 实时或准实时屏幕感知 | 高 | 已有视觉模型调用链路 | 隐私、成本、误判 |
| 屏幕分析回复 | 高 | 可复用 VLM 与上下文构建 | 复杂页面理解 |
| 网页读取 | 高 | 已有网页代理原型 | 敏感网页、跨域、登录态 |
| 网页操控 | 高 | 已有 DOM 动作执行原型 | 表单、提交、支付风险 |
| 简单电脑操控 | 中 | 可通过 pyautogui / pywin32 实现 | 高风险、误操作 |
| 自主电脑操作 | 低到中 | 小女仆可执行本地代码 | 不建议默认开放 |

结论：建议将桌宠化作为一个独立未来扩展方向推进，优先实现陪伴、状态感知和按需视觉分析，再逐步开放网页辅助与受限电脑操控。

## 4. 推荐总体架构

建议新增独立运行时：`DesktopPet Runtime`。

```text
DesktopPet Runtime
    │
    ├─ Perception 感知层
    │   ├─ 屏幕截图
    │   ├─ 活跃窗口标题
    │   ├─ 前台应用进程
    │   ├─ 键鼠空闲时间
    │   ├─ 网页 DOM 快照
    │   └─ 主人状态判断
    │
    ├─ World State 世界状态层
    │   ├─ 当前屏幕摘要
    │   ├─ 当前窗口上下文
    │   ├─ 主人是否在
    │   ├─ 主人是否忙碌
    │   ├─ 最近交互事件
    │   └─ Yuki 自身状态
    │
    ├─ Decision 决策层
    │   ├─ 是否说话
    │   ├─ 是否继续观察
    │   ├─ 是否睡觉
    │   ├─ 是否自娱自乐
    │   ├─ 是否请求截图分析
    │   ├─ 是否准备执行动作
    │   └─ 是否请求主人授权
    │
    ├─ Action 执行层
    │   ├─ 桌宠气泡
    │   ├─ 桌宠动画
    │   ├─ 网页动作
    │   ├─ 简单电脑动作
    │   ├─ 剪贴板辅助
    │   └─ 动作结果回传
    │
    └─ Audit 安全审计层
        ├─ 权限模式
        ├─ 动作风险分级
        ├─ 敏感页面检测
        ├─ 用户确认
        ├─ 操作日志
        └─ 紧急停止
```

该架构与现有 QQ 消息系统并行，不直接破坏现有主流程。

## 5. 模块规划

### 5.1 desktop_pet/runtime.py

职责：

- 启动桌宠运行时。
- 初始化 UI、感知层、状态层、动作层。
- 与现有 YukiEngine、YukiState、HistoryManager、MemoryRAG 进行依赖注入。
- 管理后台任务生命周期。

运行模式建议：

```text
python -m desktop_pet.runtime
```

或在未来主程序中增加启动参数：

```text
python main.py --desktop-pet
```

### 5.2 desktop_pet/state.py

职责：维护桌宠世界状态。

建议状态字段：

```text
pet_state: awake / watching / talking / thinking / playing / sleeping / away_mode
owner_present: true / false / unknown
owner_idle_seconds: int
current_window_title: str
current_process_name: str
current_url: str | None
last_screen_summary: str | None
last_owner_interaction_at: datetime
last_pet_initiative_at: datetime
initiative_fail_count: int
permission_mode: observe_only / assist_web / assist_desktop / high_risk_dev
```

### 5.3 desktop_pet/perception.py

职责：采集环境信息。

建议分为轻量感知与重型感知。

轻量感知：

- 当前窗口标题。
- 当前前台进程。
- 键鼠空闲秒数。
- 是否锁屏。
- 是否全屏。

重型感知：

- 屏幕截图。
- 局部截图。
- 视觉模型分析。
- OCR 或 UI 元素分析。

默认只启用轻量感知。重型感知必须在主人授权或明确触发条件下进行。

### 5.4 desktop_pet/screen_analyzer.py

职责：屏幕截图分析。

建议流程：

```text
截图请求
  ↓
检查权限模式
  ↓
检查敏感窗口/敏感标题
  ↓
截图或局部截图
  ↓
压缩与脱敏
  ↓
调用视觉模型
  ↓
生成结构化摘要
  ↓
写入 World State
  ↓
交给 YukiEngine 生成回复
```

视觉模型输出建议结构：

```json
{
  "scene": "当前屏幕大致场景",
  "active_app": "推测应用",
  "visible_task": "主人可能正在做什么",
  "risk": "normal/privacy/sensitive/unknown",
  "suggested_response": "Yuki 是否适合说话",
  "summary_for_llm": "可放入对话上下文的摘要"
}
```

### 5.5 desktop_pet/proactive.py

职责：主动行为决策。

该模块可以从现有 `ice_break_monitor()` 抽象而来，成为桌宠版主动监视器。

触发条件：

- 主人在电脑前。
- 空闲时间达到阈值。
- 当前不是会议、游戏、全屏视频等专注场景。
- 当前时间处于 Yuki 活跃区间。
- Yuki 精力充足。
- 最近没有主动打扰过。
- 最近主动搭话没有连续失败。

主动行为类型：

- 问候。
- 轻提醒。
- 记忆回顾。
- 屏幕上下文吐槽。
- 请求是否需要帮助。
- 仅显示动画，不发言。

### 5.6 desktop_pet/action_guard.py

职责：所有现实动作的安全审查。

任何网页动作、桌面动作、文件动作、命令动作都必须先经过 ActionGuard。

审查输入：

```text
action_type: click / type / scroll / navigate / screenshot / open_app / hotkey / command / file
target_app: chrome / explorer / vscode / unknown
target_url: 当前网页 URL
target_selector: 网页元素选择器
target_text: 将要输入的文本
source: yuki / maid / user / scheduled
context: 当前环境摘要
```

审查输出：

```text
allowed: true / false
risk_level: safe / low / medium / high / forbidden
requires_confirm: true / false
reason: 审查原因
redacted_preview: 给用户看的动作预览
```

### 5.7 desktop_pet/browser_bridge.py

职责：将现有 `webpage_agent` 原型升级为正式网页桥接层。

改造方向：

- 将 HTTP 服务与 Yuki 主运行时解耦。
- 页面快照不直接打印，而是进入 World State。
- 元素列表转为可供 LLM 读取的页面摘要。
- 动作队列必须经过 ActionGuard。
- 支持动作结果写回当前会话。
- 支持敏感 URL 拦截。

### 5.8 desktop_pet/desktop_controller.py

职责：执行受限桌面动作。

建议初期只支持：

- 打开指定 URL。
- 打开 Yuki 自己的设置窗口。
- 复制文本到剪贴板。
- 移动桌宠窗口。
- 读取当前窗口标题。

暂不建议支持：

- 任意键盘输入。
- 任意鼠标点击。
- 任意命令执行。
- 自动删除文件。
- 自动提交表单。

## 6. 桌宠状态机设计

推荐状态：

```text
awake      醒着，准备互动
watching   安静观察，不主动打扰
thinking   思考中，可能在整理记忆或分析上下文
talking    正在说话
playing    自娱自乐，如换姿势、看日记、摆弄表情
sleeping   睡觉，低频或停止感知
away_mode  主人不在，降低活动频率
```

状态转换示例：

```text
owner_active + yuki_energy_high → awake
owner_active + user_busy → watching
owner_idle_long + yuki_energy_high → proactive_check
proactive_check_pass → talking
owner_absent → away_mode
late_night + low_activity → sleeping
owner_returns → awake
```

行为原则：

- `sleeping` 状态不应频繁截图或调用 LLM。
- `watching` 状态只做轻量感知，不主动打扰。
- `talking` 状态要有冷却时间，避免连续弹气泡。
- `playing` 状态只能做低风险自我行为。
- `away_mode` 可以整理记忆，但不应执行外部动作。

## 7. 主动聊天设计

### 7.1 主动聊天触发条件

建议综合以下因素：

- 当前时间权重。
- Yuki 精力值。
- 主人空闲时间。
- 当前应用类型。
- 主人最近是否与 Yuki 互动。
- 最近主动搭话是否被回应。
- 当前是否可能是敏感场景。

### 7.2 主动聊天类型

#### 轻陪伴型

适合低打扰场景：

- “我在旁边趴一会儿，不打扰你。”
- “学长还在忙呀，我安静看着。”
- “感觉你停在这里好久了，是在思考吗？”

#### 上下文辅助型

需要屏幕摘要或窗口标题：

- “看起来你在写代码，要不要我帮你整理一下思路？”
- “这个页面好像信息很多，需要我帮你概括吗？”
- “如果这里卡住了，可以叫我一起看看。”

#### 记忆驱动型

从日记或长期记忆触发：

- “之前你说想继续做某个功能，今天要不要推进一点？”
- “我想起你上次提到的计划了，要不要我帮你列一下？”

#### 状态提醒型

结合时间与活动：

- 晚上提醒休息。
- 长时间工作提醒喝水。
- 午饭时间提醒吃饭。
- 深夜降低活跃度并进入睡觉状态。

### 7.3 防打扰机制

必须设置：

- 主动搭话冷却时间。
- 主动搭话失败计数。
- 专注应用黑名单。
- 全屏场景静默。
- 会议/游戏/视频场景静默。
- 一键关闭主动聊天。

## 8. 屏幕截图与分析规划

### 8.1 不建议真正实时分析

“实时截屏”技术上可行，但默认不应做连续高频截图。建议采用：

- 默认轻量感知。
- 事件触发截图。
- 主人主动请求截图。
- 低频抽样截图。
- 敏感场景直接拒绝。

推荐策略：

```text
默认：不截图，只读取窗口标题和空闲时间。
主人询问“你看看屏幕”：截图一次并分析。
Yuki 想主动帮忙：先请求授权，再截图。
网页桥接可用时：优先读取 DOM 摘要，不截屏。
```

### 8.2 隐私过滤

敏感关键词示例：

```text
password, 密码, login, 登录, 支付, 银行, bank, wallet, token, key,
邮箱, 私信, 私聊, 账单, 订单, checkout, pay, alipay, wechat pay,
后台管理, production, admin, secret, credential
```

命中敏感场景时：

- 不发送截图到视觉模型。
- 不记录屏幕内容。
- 只返回安全提示：当前可能是隐私页面，Yuki 不看。

### 8.3 成本控制

屏幕分析应避免高频 VLM 调用：

- 截图先压缩。
- 对同一窗口标题/页面短时间内复用摘要。
- 只分析局部区域。
- 分辨率限制在较低尺寸。
- 对静止页面做 hash 去重。

## 9. 网页读取与操控规划

### 9.1 基于现有原型升级

当前 `webpage_agent` 原型采用“浏览器脚本扫描 DOM + 后端队列下发指令”的方式，该模式适合保留。

升级目标：

- `yuki_eye.user.js` 继续负责页面扫描与动作执行。
- 后端从临时命令行程序升级为 BrowserBridge 服务。
- 页面状态进入桌宠 World State。
- LLM 只看到页面摘要和可交互元素摘要。
- 所有动作先经过 ActionGuard。

### 9.2 页面摘要格式

建议将元素列表转换为更适合 LLM 理解的结构：

```text
页面标题：xxx
当前 URL：xxx
页面主要内容摘要：xxx
可交互元素：
- #0 按钮：搜索
- #1 输入框：请输入关键词
- #2 链接：文档
风险判断：normal / sensitive
```

### 9.3 网页动作分级

安全动作：

- 滚动。
- hover。
- focus。
- 读取页面元素。
- 打开普通搜索页面。

中风险动作：

- 点击普通按钮。
- 输入非敏感文本。
- 切换选项。
- 打开链接。

高风险动作：

- 提交表单。
- 登录。
- 注册。
- 上传文件。
- 发送消息。
- 下单。
- 支付。
- 删除内容。

高风险动作必须逐次确认。

## 10. 简单电脑操控规划

### 10.1 技术可行方式

Windows 下可能使用：

- `pywin32`：窗口信息、进程信息、部分系统 API。
- `pyautogui`：鼠标键盘动作。
- `pyperclip`：剪贴板。
- `mss`：截图。
- `psutil`：进程状态。

### 10.2 初期允许动作

建议初期只允许：

- 打开 Yuki 自己的窗口。
- 打开指定 URL。
- 复制文本到剪贴板。
- 读取当前窗口标题。
- 读取用户空闲时间。
- 控制桌宠自身位置、透明度、表情。

### 10.3 默认禁止动作

默认禁止：

- 任意鼠标点击。
- 任意键盘输入。
- 自动发送消息。
- 自动执行命令行。
- 自动删除/移动文件。
- 自动安装软件。
- 自动修改系统设置。
- 自动提交网页表单。
- 自动上传文件。

如果未来要开放，必须在高风险开发模式中逐次确认。

## 11. 权限与安全体系

### 11.1 权限模式

建议提供四级权限：

#### observe_only：只观察模式

- 允许桌宠 UI。
- 允许读取时间、空闲状态、窗口标题。
- 不允许截图。
- 不允许网页动作。
- 不允许桌面动作。

#### assist_screen：屏幕辅助模式

- 允许主人主动请求截图分析。
- 允许低频窗口摘要。
- 不允许自动截图。
- 不允许动作执行。

#### assist_web：网页辅助模式

- 允许读取网页 DOM 摘要。
- 允许低风险网页动作。
- 中风险动作需要确认。
- 高风险动作默认禁止或逐次确认。

#### high_risk_dev：高风险开发模式

- 允许更多桌面动作。
- 每次启动必须重新确认。
- 所有动作必须记录审计日志。
- 必须提供紧急停止按钮。

### 11.2 动作风险分级

```text
safe      纯内部行为，不影响外部环境
low       可逆、低影响动作
medium    可能改变网页/应用状态，需要确认
high      可能发送、提交、修改、删除、上传，需要强确认
forbidden 默认禁止，不允许自动执行
```

### 11.3 必须具备的安全能力

- 全局暂停。
- 一键停止所有动作。
- 敏感页面黑名单。
- 动作预览。
- 用户确认弹窗。
- 操作日志。
- 权限模式可视化。
- 高风险模式启动警告。

## 13. 分阶段实施路线

### Phase 1：桌宠外壳

风险：低。

- 当前前台进程。
- 全屏状态检测。
- 主人不在时进入 away_mode 或 sleeping。

风险：中低。  
优先级：高。

目标：让 Yuki 更像活着的桌宠。

优先级：高。

### Phase 4：按需屏幕分析

内容：

- 主动请求截图权限。

### Phase 5：网页读取与辅助操作

风险：高。

### Phase 6：受限桌面操控

## 15. 关键风险与控制措施

### 15.1 隐私风险

风险：截图、网页读取可能包含密码、私聊、支付、工作机密。

控制：

- 默认不截图。
- 敏感窗口拒绝分析。
- 本地权限开关。
- 不保存原始截图。
- 高风险页面只返回安全提示。

### 15.2 操作风险

风险：误点击、误输入、误提交、误删文件。

控制：

- 动作分级。
- 中高风险确认。
- 默认禁止不可逆动作。
- 操作前预览。
- 操作后日志。

### 15.3 打扰风险

风险：主动聊天过于频繁，影响主人工作。

控制：

- 冷却时间。
- 专注模式。
- 全屏静默。
- 主动搭话失败次数限制。
- 一键关闭主动模式。

### 15.4 成本风险

风险：屏幕分析频繁调用视觉模型，成本和延迟高。

控制：

- 事件触发。
- 截图 hash 去重。
- 局部截图。
- 摘要缓存。
- 低频调用。

### 15.5 自主代理失控风险

风险：小女仆或 LLM 自主执行超出预期的本地操作。

控制：

- 小女仆不直接接触桌面控制器。
- 所有动作经过 ActionGuard。
- 高风险开发模式单独开关。
- 禁止自动命令执行。

## 16. 推荐最终产品定位

Yuki 桌宠不应定位为“全自动电脑控制 AI”，而应定位为：

```text
有身体的陪伴型 AI
→ 能感知主人状态
→ 能低打扰主动互动
→ 能在授权下理解屏幕
→ 能辅助网页操作
→ 能有限、可控地影响现实电脑环境
```

最符合项目气质的方向是“有生活感、边界感、陪伴感”的桌宠，而不是“强执行、强侵入、自动化接管”的代理。

现实侵入性可以逐步增强，但必须建立在以下原则上：

- 主人知道 Yuki 看到了什么。
- 主人知道 Yuki 想做什么。
- 主人可以阻止 Yuki。
- Yuki 不在敏感场景擅自行动。
- 所有高风险行为都可追溯。

## 17. 结论

YukiV6 扩展为桌宠具有较高可行性。项目已有的记忆、人格、精力、生物钟、主动破冰、视觉模型、小女仆和网页代理原型，为桌宠化提供了扎实基础。

推荐采用渐进式路线：

```text
桌宠 UI
→ 主人状态感知
→ 主动聊天/睡觉
→ 按需屏幕分析
→ 网页读取辅助
→ 受限电脑操控
→ 自主日常行为
```

其中，屏幕分析、网页操控和电脑操控是高风险能力，必须配套 ActionGuard、权限模式、敏感场景检测和操作日志。

只要安全边界设计得当，Yuki 可以从 QQ 聊天助手自然演进为真正“住在电脑里的桌宠”。
